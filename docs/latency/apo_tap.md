# APO tap feasibility (audio-engine tap instead of cable capture)

> Purpose: feasibility of tapping the Windows audio engine with an APO instead of capturing a cable.
> Date: 2026-10-10 (this report: research only, nothing installed). Method: read-only registry and file inspection, string scan of a copy of the Equalizer APO DLL, model of the router latency.
> Back to the [documentation index](../README.md).
>
> Corrections/updates: the "about 20 to 25 ms" (VAC Line 1 at 1 ms) and "19 to 25 ms" (low-period endpoint) rows in section 6 are not reachable with VAC lite; measured later in [vac_lite.md](vac_lite.md) (capture floor 5 ms clean, supported default 6 ms), the estimate there is about 26 to 34 ms. The APO verdict is unchanged.

Status: research only. Nothing was installed, registered, loaded or written. Date 2026-10-10, Windows 11 25H2 (build 26200.9457).
Evidence was gathered read-only: registry reads, file listings, a string scan of a *copy* of `EqualizerAPO.dll` in the scratchpad, and a query-limited process handle on audiodg.

## 0. Verdict (short)

* Technically feasible, and the machine is already prepared (audiodg is unprotected, an unsigned APO is already installed, `DisableProtectedAudioDG=1`).
* Expected gain on a 10 ms endpoint (Hi-Fi Cable or AORUS): **about 18 to 23 ms** (56.2 -> roughly 33 to 38 ms). That does NOT reach the 25 ms goal. A block still arrives only once per engine period, so staleness (b/2 = 5 ms) and a ring dip of about P/2 remain. The premise "capture-side latency about 0" is wrong: the tap removes the cable transport and the irregular pair delivery, not the per-block cost.
* The 25 ms goal is reachable only with a small endpoint period (1 to 2.7 ms). Then a plain WASAPI capture of that low-period source (VAC Line 1 at 1 ms, VBMatrix) gets most of the same benefit with no system risk.
* Risk is dominated by system stability (an APO bug kills all system audio) and by one more unsigned DLL inside audiodg for a gaming user. Effort 6 to 10 days for a safe prototype.
* Recommendation: do NOT build the production APO now. Run the cheap measurement gate (section 6) first: the engine periods of the AORUS endpoint and of VAC Line 1 / VBMatrix. Build the APO prototype only if no usable low-period source exists and about 35 ms on a 10 ms endpoint is worth the risk.

## 2. APO architecture facts that matter here

* An APO is an in-proc COM object implementing `IAudioProcessingObject` (format negotiation, `GetLatency`, `GetRegistrationProperties`), `IAudioProcessingObjectRT` (`APOProcess`, `CalcInputFrames`, `CalcOutputFrames`) and `IAudioProcessingObjectConfiguration` (`LockForProcess`/`UnlockForProcess`). Windows 10+ also expects the `IAudioSystemEffects` marker (and optionally `IAudioSystemEffects2/3`, `IAudioProcessingObjectNotifications`). Reference code is in this repo: `Windows-driver-samples\audio\sysvad\APO\SwapAPO` and `DelayAPO` (MS-PL), and the HLK tests in `audio\tests\HLK\ThirdPartyApoTests`.
* `APOProcess` is called by the engine's real-time thread **once per engine pass** (one endpoint period: 10 ms on most shared endpoints, shorter if an IAudioClient3 client lowered the endpoint period) with float32 data in the endpoint mix format fixed by `LockForProcess`. With Flags=13 the APO is in-place and the format is guaranteed. The frame count can vary; silent input is flagged `BUFFER_SILENT` (the buffer may be uninitialised: treat as zeros).
* Stages: **SFX** (per stream, before the mix), **MFX** (post-mix, per processing mode), **EFX** (endpoint, last stage before the endpoint buffer). Legacy LFX/GFX map to pre-mix/post-mix. To tap everything on an endpoint, MFX or EFX sees the final mix, the same thing WASAPI loopback would capture. EFX is the natural place; MFX is skipped by RAW-mode streams. The prototype must test both (details of mode bypass with enhancements disabled are unverified on this build).
* `GetLatency` returns the delay the APO adds (100 ns units). A memcpy tap adds 0 and must report 0.
* The APO runs inside audiodg on a real-time thread: no allocation, no locks, no IO or logging, no blocking waits, no panic across FFI. Create and size all shared objects at construction or in `LockForProcess`, never in `APOProcess`.
* Process model: audiodg is LocalService in **session 0**. A user-session app cannot open the APO's `Local\` objects and cannot create `Global\` objects (SeCreateGlobalPrivilege). So the **APO side creates** `Global\...` mapping and event with an explicit security descriptor (for example SDDL `D:(A;;GA;;;SY)(A;;GRGW;;;AU)`), and the router opens them with `OpenFileMappingW`/`OpenEventW`. The existing `router-core::status_writer` already creates a named mapping with `CreateFileMappingW` (default security); the APO needs the same with explicit `SECURITY_ATTRIBUTES` and the `Global\` prefix.
* Consumer absent: the producer never waits. Overflow policy as in `router-core::ring::Producer::push_frames`: drop the newest block and count it. The consumer trims latency by discarding the oldest frames (`Consumer::discard`). A stalled write index (no engine pass because no stream is rendering) means silence to the consumer. A generation counter bumped in `LockForProcess` lets the consumer detect format changes and restarts.
* Failure consequences: audiodg is shared by every endpoint. An access violation in an APO kills audiodg and all system audio; Audiosrv restarts it automatically but apps see device invalidation and many games lose sound until restarted. A slow `APOProcess` makes the whole engine glitch. A misregistered CLSID is usually skipped by the engine (stream plays without the effect); a crashing `DllMain` is worse.

## 3. Registration mechanics and Rust sketch

* A custom APO needs (1) the COM class under `HKLM\SOFTWARE\Classes\CLSID\{clsid}\InprocServer32` (ThreadingModel Both), (2) the same CLSID under `HKLM\SOFTWARE\Classes\AudioEngine\AudioProcessingObjects\{clsid}` with FriendlyName, Copyright, versions, **Flags** (13 as Equalizer APO, or 15 to also demand matching channel count), 1/1 connections, APOInterface0, (3) the endpoint's `MMDevices\Audio\Render\{guid}\FxProperties` value `{d04e05a6-...},7` (EFX) or ,6 (MFX) set to the CLSID. Step 3 needs admin plus ownership of the MMDevices keys (the Equalizer APO DLL contains `AllocateAndInitializeSid` "taking ownership" paths for this). Windows re-reads FxProperties only when the endpoint is rebuilt: restart the Windows Audio service, toggle the device, or reboot. Equalizer APO's install follows exactly this pattern and keeps a rollback copy (section 1.1).
* The Hi-Fi Cable endpoint currently has no FxProperties, so the composite proxy is not present there. Whether a direct `,7` value is honoured on it is unproven. SFX/MFX (,5/,6) is known to work on this machine (Equalizer APO on VBMatrix In 3).
* Windows 11 "Audio enhancements" / "Disable all enhancements" bypasses SFX/MFX processing of an endpoint. If the user toggles it, an MFX tap goes silent; the router must detect "no blocks while the endpoint is active" and fall back to cable capture. Spatial audio and loudness equalization are themselves APOs (`CAdaptiveSpatialAudioRenderer`, `CAudioLimiter`); keep the tap last (EFX) and spatial audio off on that endpoint.
* Per-app volume is applied in the mixer before MFX, so the tap sees the post-per-app-volume mix, like loopback. Endpoint master volume and mute are applied after the endpoint stage, so **endpoint volume and mute do not change what the tap sees**. In the AORUS scenario the monitor can stay muted.
* Rust sketch (not to be written now): `crates/eq-asio-apo`, `cdylib`, x86_64-pc-windows-msvc, `windows` crate `#[implement(IAudioProcessingObject, IAudioProcessingObjectRT, IAudioProcessingObjectConfiguration, IAudioSystemEffects)]`, static CRT (`+crt-static`) so audiodg needs no VC runtime. Do not use `panic = "abort"` in this DLL (an abort kills audiodg); wrap every entry point in `catch_unwind` and fail closed (audio passes untouched). Shared block: header (magic, version, generation, rate, channels, capacity, write index, drop counter, QPC of the last pass) plus an interleaved float32 ring, with the same Release/Acquire SPSC scheme as `router-core::ring` over raw mapped memory (`AtomicU32::from_ptr` as in `status_writer.rs`). `APOProcess`: `copy_nonoverlapping` into the ring, release-store the write index, `SetEvent` (non-blocking), leave the buffer unchanged. Consumer: an `ApoSource` capture implementation in the router that waits on the event, reads whole blocks and feeds the existing sink (`on_frames`), so `arrival.rs` measures the real pattern with no changes.

## 4. Latency impact model

Inputs from the code: `arrival.rs` (target = block + safety + 1.25 x dip p99.9 + 2 look-ahead; a regular train with gap G has dip = r G / 2; staleness = E[b^2] / (2 r E[b]) = b/2 for regular blocks) and `stream_integrity.rs` (the same formula checked on the cable's pairs). Yamaha block 256 frames, safety 2 ms, 48 kHz. I add a 1 ms p99.9 engine-thread jitter allowance (48 frames) to the dip of the new sources; J=0 values are in brackets. Yamaha out stays 7.8 ms. The render side (app buffer to engine pass) is the earlier unmeasured estimate of ~10 ms on the cable path, which includes the cable driver's endpoint buffer and transport. For the tap it is split into the app-to-engine part only: about P/2 wait plus game buffer.

Today (measured): Yamaha 7.8 + ring 27.6 + staleness 9.2 + render ~10 = **56.2 ms**. Formula check for today's pairs (dip 480 fr): target = 256 + 96 + 1.25 x 480 + 2 = 954 fr = 19.9 ms against 27.6 measured, so about 7.7 ms is not explained by the model (extra arrival jitter, start-up bias, controller wander). The pessimistic column keeps that offset; the expected column assumes it was caused by the irregular pairs and disappears with regular blocks.

| Source / endpoint period | dip p99.9 (fr) | ring target ms (formula) | staleness ms | Yamaha ms | render side ms | Total expected | Total pessimistic (+7.7) |
|---|---|---|---|---|---|---|---|
| Hi-Fi Cable via WASAPI, 10 ms packets in pairs (today) | 480 | 19.9 (27.6 measured) | 9.2 | 7.8 | ~10 | **56.2 measured** | 56.2 |
| APO tap on Hi-Fi Cable Input, P = 10 ms regular | 240 + 48 = 288 | 14.9 [13.6] | 5.0 | 7.8 | 5 to 10 | **33 to 38** [31 to 36] | 40 to 46 |
| APO tap on AORUS, P = 10 ms regular | 288 | 14.9 [13.6] | 5.0 | 7.8 | 5 to 10 | **33 to 38** | 40 to 46 |
| Hypothetical APO on P = 2.667 ms (VBMatrix In 3 type) | 64 + 48 = 112 | 10.3 [9.0] | 1.3 | 7.8 | 3 to 5 | **23 to 25** | 31 to 33 |
| Hypothetical APO on P = 1 ms (VAC Line 1 type) | 24 + 48 = 72 | 9.3 [8.0] | 0.5 | 7.8 | 1 to 2 | **19 to 20** | 27 to 28 |

What is actually removed, term by term, on a 10 ms endpoint:
* Ring: 27.6 -> about 14.9 ms (-12.7): one regular block per pass instead of a 960-frame pair every 20 ms (dip 240 instead of 480 frames).
* Staleness: 9.2 -> 5.0 ms (-4.2): 10 ms events instead of 20 ms events.
* Render side: the tap sits in the engine pass **before** the endpoint buffer, so the cable driver's render buffer and transport to its capture side (pinned 10 ms period) are skipped entirely, and no capture-stack wake-up happens. Gain 0 to 5 ms (uncertain; the 10 ms estimate was never measured).
* Not removed: a block can only be forwarded after the whole pass, so each frame still waits b/2 = 5 ms on average, and the ring still needs about P/2 headroom. Only a smaller engine period reduces those terms, and the APO does not control the period (the endpoint driver and IAudioClient3 clients do).
* The tap sees audio about one engine period before the endpoint hardware plays it. Versus a WASAPI loopback of the same endpoint it saves the capture-stack buffering/wake-up (about 0 to one period, not measured here) and needs no keep-alive stream. Versus the cable it saves about 18 to 23 ms.

## 5. Interaction with the user's setup and risks

* APO order: on Hi-Fi Cable Input the tap would be alone. On AORUS the Microsoft Home Theater APOs occupy SFX/MFX, so the tap should be EFX (,7), i.e. last. Equalizer APO is on neither endpoint; keep it off the router's endpoint, otherwise the router would receive the Peace-EQ'd signal and then apply AutoEQ again.
* AORUS scenario: Windows default = AORUS, the tap reads the mix before the monitor; the monitor can stay unused. It works only while the NVIDIA endpoint exists (monitor link up). The AORUS engine period is unknown until measured with `GetSharedModeEnginePeriod`; Hi-Fi Cable is pinned at 10 ms (fundamental = min = max = 480 fr).
* Silence/sleep: the engine pass stops when no stream renders on the endpoint; the router must treat a stalled index as silence and keep its output alive.
* `DisableProtectedAudioDG=1`: audiodg is not a PPL, so any administrator-installed DLL can run in the audio engine and the audio graph loses a protection layer. It is a known, widely used tweak for unsigned APOs and already applied here; the incremental risk of a second unsigned APO is small, the existing exposure is the same class. Windows Update has not reset it (present on 25H2 build 9457), but a driver reinstall or endpoint re-enumeration recreates FxProperties and silently detaches an APO (Equalizer APO's Configurator has the same weakness).
* Signing: if audiodg PPL were re-enabled, third-party APOs would need Microsoft-trusted signing (WHQL/attestation with the right EKU). That is out of reach for a personal project, so the tap depends on the tweak staying honoured by Windows.
* Anti-cheat: kernel anti-cheats (Vanguard, EAC, BattlEye, FACEIT) inspect the game process and loaded drivers, not audiodg. This machine already has the same state (unsigned Equalizer APO, unprotected audiodg) and I found no documented requirement for PPL audiodg in these products, but I cannot prove they never check it (they change). New exposure: a second unsigned DLL in audiodg, and a `Global\` shared section that exposes game audio to any logged-on user (a privacy surface only). Residual risk low to moderate; mitigate by testing with the actual games and keeping a one-click revert. EasyAntiCheat services are present but stopped.
* Stability: the highest risk. A bug takes down audiodg and all audio. Mitigations: `catch_unwind`, no allocation, bounded work (a memcpy), fail-closed pass-through, a kill switch read at `LockForProcess`, soak on a throwaway endpoint first.
* Licensing: Equalizer APO is GPL-2.0 and Peace is a separate GUI; do not copy their code (only the public registration pattern was studied). The Microsoft SwapAPO/DelayAPO samples are MS-PL and can be adapted. No Steinberg/Yamaha licence is involved (the ASIO side is untouched). Distributing an unsigned DLL loaded by audiodg to other people needs a clear warning; fine for personal use.

## 6. Verdict, alternatives and plan

| Option | Total latency (expected) | Gain vs 56.2 | Risk | Effort | Reversibility |
|---|---|---|---|---|---|
| Stay on Hi-Fi Cable + planned P0/P1 tuning (burst model, Yamaha 128) | about 33 to 35 (plan estimate) | ~21 | none | in the plan | n/a |
| VAC Line 1 (1 ms) or VBMatrix (2.667 ms) as WASAPI source | about 20 to 25 (1 ms: 19 to 20 ideal; not currently enumerable as an active capture) | up to 35 | low (no system change; depends on the third-party driver) | 1 to 3 days | trivial |
| WASAPI loopback of AORUS (10 ms unless the HD Audio driver allows less) | about 38 to 45 | 11 to 18 | low | 3 to 5 days (plan P2/P3) | trivial |
| APO tap on a 10 ms endpoint (Hi-Fi Cable / AORUS) | **33 to 38 (up to 46 pessimistic)** | 18 to 23 | **moderate**: audiodg stability, extra unsigned DLL, anti-cheat unknowns | **6 to 10 days** | medium (registry edit + audio service restart; revert script easy) |
| APO tap on a low-period endpoint | 19 to 25 | 31 to 37 | same | same | same; a WASAPI capture of such an endpoint is within ~2 to 4 ms of this |

Decision: an APO tap on a 10 ms endpoint lands near 35 ms, about the same as the already-planned tuned cable path, because both are bounded by the 10 ms period. It adds real value only in the narrow case "the driver pins 10 ms and nothing better exists", where it saves the cable transport (0 to 5+ ms) and the pair irregularity (about 8 to 17 ms). It is not required to reach the goal when a low-period endpoint can be captured with plain WASAPI.

Recommended next steps (no system changes until gated):
1. Gate A, read-only and cheap: `capture-probe info` for the engine periods (default/fundamental/min/max) of the AORUS endpoint, VAC Line 1 and VBMatrix In 3, plus a 30 s arrival capture. If a source with period <= 3 ms and regular arrivals works, use it and shelve the APO.
2. If A fails and the user still wants the tap, Phase 1 (1 to 2 days): define the shared-memory block format and an `ApoSource` consumer in the router with a Rust test producer at a fixed cadence (no audiodg). Extend `stream_integrity.rs` with "regular P = 10 ms + 1 ms jitter" to confirm the model's 14.9 ms target.
3. Phase 2 (2 to 3 days): write `eq-asio-apo` and test it outside audiodg (a host exe that creates the COM class and calls `APOProcess` with synthetic buffers: counting allocator proves no allocation, silent flag, rate change, LockForProcess/Unlock cycles, `catch_unwind`).
4. Phase 3 (1 to 2 days): throwaway endpoint test only on a disposable device (CABLE Input, which has no FxProperties and no consumers) or a dummy virtual device. Install script: `reg export` the endpoint's FxProperties, copy the DLL, write the CLSID keys and the single FxProperties value, restart Audiosrv. Mirror revert script: delete the value, import the export, remove the CLSID keys, restart Audiosrv. Verify: Equalizer APO still works on its endpoints, no audiodg crash events in the Application log over a 30 min soak, 0 router underruns, end-to-end latency via `router-cli latency`.
5. Phase 4 (1 to 3 days): soak on the real endpoint and in the user's games (with anti-cheat), keep the revert script, and make the router fall back to cable capture automatically when the APO block counter stalls.

Unknowns that could not be settled read-only: acceptance of EFX (,7) on a driver-less endpoint like Hi-Fi Cable; MFX/EFX behaviour with RAW mode or "enhancements disabled" on this build; the true render-side numbers; the AORUS engine period; the unexplained 7.7 ms between the formula and the measured ring today.
